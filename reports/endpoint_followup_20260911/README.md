## プロファイルで判明した重複

最適化前のPEPC scanでは、cProfile実行中の30.5秒のうち、joint推定が20.3秒、
その中のコドン対からの集約が17.4秒を占めた。検証段階と候補評価段階で
exposure用の遷移行列も2回構築していた（合計3.2秒）。scanとsitesはどちらも、
直後に再計算する内部ノードの祖先確率の読み込みに約2.5秒を使っていた。

これは改善対象を決めるためのプロファイルであり、性能比較の測定とは別。
cProfileのオーバーヘッドを含む。各段階のRSSは入口・出口の値で、段階内の
ピーク値ではない。

## 変更

1. **不要な入力・重複配列を削減。** 通常のunrecoded joint sites/scanでも、
   先端の観測と状態ファイルのヘッダだけを読み、再計算する祖先確率は読み込まない。
   scanで推定前の`zero_sub_mass`フィルタが必要な場合や別のrecodingでは従来どおり読む。
   同一の観測AA配列とN配列を共有し、CLIはparametric校正・解析的尤度で再利用しない
   元のコドン観測配列を推定後に解放する。並列置換校正workerには、既に注釈へ変換した
   観測状態配列を送らない。
   CLIの呼び出し元が持つ設定も同じ推定済み配列へ更新し、古い配列への参照を残さない。
2. **scanの大きな中間配列を省略。** 既存のclassified endpoint reducerを再利用して
   Nイベントを直接集計し、S総量はマスク付き遷移行列から直接求める。
   native拡張なしの経路も維持する。モデル検証とexposure遷移行列の構築を分離し、
   推定前に作って捨てていた遷移行列を省く。
3. **sitesの非対象枝を集計専用にする。** 指定枝の詳細イベントは保持し、
   非対象枝では全体サマリに必要な総量だけを直接計算する。全枝を使うサイト集計は残る。
   通常の全イベント保持経路でも、使わない周辺集計を作らない。

当初の候補別キャッシュより、測定で支配的だったコドン対展開と重複した遷移行列を
優先した。入力全体の状態配列をディスクへ移す大規模な変更は今回行っていない。
全ノード×全サイトの周辺状態は引き続きRAMに残るため、RAMは入力規模に応じて増える。
今回の一時ファイルの形式・保存精度・容量は前回と同じ。

## 検証と測定条件

- 通常テスト2,248件成功、5件skip。nativeテスト16件成功。
  Ruff、repository hygiene、documentation checkと全23対象のmypyが成功。
- native拡張を無効にした関連テスト157件成功、native専用10件skip。
  呼び出し元の参照・入力保持の3テストも拡張なしで成功した。
- 未ロードの内部ノードからのscan、rate mixture、独立な全イベント集計との一致、
  recoding/フィルタ時の入力保持、配列共有、workerへの不要配列の混入を検証した。
  通常scanでは元の配列が解放され、parametric校正・解析的尤度では必要な観測が
  保持されることを、実行後の弱参照でも検証した。
- [全体検査ログ](checks.log)、[拡張なしの検査ログ](checks-fallback.log)。
  [配列寿命テスト](checks-lifetimes.log)、[同テストの拡張なし実行](checks-lifetimes-fallback.log)。

性能測定とは別に、PGK/PEPCの通常検索、PGKの解析的P値付きscan、3反復parametric校正、
`zero_sub_mass`フィルタ付きscan、`min_sub_pp=0.05`のsitesも変更前後で実行した。
6設定すべてで主結果TSVの全列が一致した。解析的scanでは127列、parametric校正では
121列を照合している。[追加比較結果と完全なコマンド](extra-output-checks.json)、
[再実行用スクリプト](check_outputs.py)。この追加比較に性能向上の主張は含めない。

各ケースはウォームアップ1回＋計測3回、変更前後の順序を交互にして逐次実行。
両版で同じPython環境・native拡張・固定IQ-TREE fit・float64・seed=8を使用する。
PEPCは71配列×971コドン、PGKは33配列×417コドン。
PEPC×4は配列・サイト情報を4回繰り返した3,884コドンの合成サイズ試験で、
独立な生物学的データではない。モデルと枝長は元のECMK07+F+R4のfitを再利用した。
IQ-TREEの再推定、プロット、ネットワーク取得は除外。BLASは1スレッド、
通常実行は1スレッド、並列校正ケースは2プロセスで20反復のfull-scan置換校正。
既定の1,000反復校正全体の時間を測ったものではない。

macOS 26.6.2、x86_64、64 GiB RAM、Python 3.10.14、NumPy 1.26.4、
SciPy 1.15.2、pandas 2.2.3。共有ホスト上で測定し、ファイルキャッシュは消去しない。
CLI全体の経過時間と`/usr/bin/time -l`のピークRSSに加え、20 ms間隔で子プロセスの
RSS合計も取得する。後者はtime wrapperとruntime helperを含み、共有ページを
重複計上し得るため、固有の物理RAM使用量ではない。短いピークを取り逃す可能性もある。

各ケースのウォームアップで、主結果TSVの全列・行順・型を照合する。
数値許容差は`rtol=1e-8, atol=1e-9`。実行時間などの動的メタデータは含めない。
完全なCLI引数、入力・ソースのSHA-256、全測定値、ホストCPU利用状況と比較結果は
[results.json](results.json)に記録する。

## 再現

基準版を`3fd379c`、候補版をこのレポートを含むコミットから別ディレクトリへ展開し、
同じ環境でnative拡張を用意する。基準側の`csubst/dataset`に同梱データを配置する。

```sh
python reports/endpoint_followup_20260911/benchmark.py \
  --baseline-root /path/to/before --candidate-root /path/to/after \
  --baseline-label 3fd379c --candidate-label endpoint-followup \
  --cases pepc_scan_defaults pepc_sites pgk_scan_parallel20 pepc4_scan_defaults pepc_full \
  --workdir /tmp/csubst-endpoint-followup \
  --result /tmp/csubst-endpoint-followup.json
```

個別の診断プロファイルは、`PROFILE_OUTPUT=/tmp/profile.json`と
`PYTHONPATH=/path/to/source`を指定して、`profile_cli.py`に通常のCLI引数を渡す。
