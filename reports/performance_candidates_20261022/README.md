# 性能改善10案の文献調査・独立検証（2026-10-22）

**採用を勧める候補は3件、条件付き候補は4件、見送りは3件。**
まず案6の候補表示処理、次に案7の候補固定校正を優先する。
Fisher urnを利用する場合は案9も有力である。
ここでいう採用候補は製品実装へ進める価値があるという意味であり、
組み込み・公開に必要な回帰検証まで完了したという意味ではない。
今回は調査と試作比較で、製品コード・科学的既定値・参照値・CIは変更していない。

## 全10案の評価

時間は同じ条件の現行版と試作のwall time中央値。
**すべて個別処理の結果であり、CLI全体の短縮率ではない。**

| 案 | 改善内容 | 判定 | 実測と判断の根拠 |
| --- | --- | --- | --- |
| [1](proposal01.md) | 完全一致サイトパターンの圧縮 | 条件付き | 人工反復PEPC×4のendpoint処理は6.660→3.247秒（51.3%短縮）。通常PGK/PEPCは約11%増で既定適用は見送り。展開時の追加メモリも必要 |
| [2](proposal02.md) | endpointのブロックサイズ調整 | 条件付き | B64→128でPGK推論18.0%、PEPC×4推論15.5%短縮。主要bufferは約2倍。scanの既存書込上限もあるため、合計メモリ予算とCLI確認が必要 |
| [3](proposal03.md) | 固有分解を共有して遷移行列を構築 | 見送り | 遷移準備は約45–47%短縮したが、微小遷移を失い、短枝のnode posteriorに最大0.9453の誤差。速度より正確性を優先 |
| [4](proposal04.md) | 疎行列spoolの断片読取りをmmap化 | 条件付き | 高次arityのPEPC CSR構築は1.858→1.529秒（17.7%中央値短縮、範囲は一部重複）。合成入力のpeak RSSは約50.6 MiB増。既定arity2の利益は未確認 |
| [5](proposal05.md) | scanのサイト別状態準備を共有 | 見送り | wall time改善を確認できず。PEPC全matchは1.423→1.454秒。snapshotとcacheで約123 MiBの追加配列を保持 |
| [6](proposal06.md) | 候補表示用の小型Series生成を省く | **優先候補** | 実PGK/PEPCの候補生成37–42%短縮。PEPC scan coreは0.408→0.359秒（12.0%短縮）。全列・型・順序・表示文字列が厳密一致 |
| [7](proposal07.md) | 候補固定校正でスコアに必要な集計だけ作る | **優先候補** | 同じ10割当てでPGK19.2%、PEPC17.8%短縮。全スコア・候補キー・反復診断が厳密一致。数値コアの共有が製品化条件 |
| [8](proposal08.md) | SiteArrayの反復読取りをmmap化 | 見送り | 返却値のsnapshot契約を維持するとPGK scan coreは14.2%悪化。合成入力のpeak RSSは約419 MiB増。copyを省く公開viewは契約不適合 |
| [9](proposal09.md) | Fisher inclusionの対数DP集約をベクトル化 | **優先候補** | 合成971サイト・draw100の関数単体は70.897→5.501 ms（12.89倍）。全13条件でdtype・shape・bytesが一致。任意Fisher経路に限定 |
| [10](proposal10.md) | endpointの行列積・要素積を既存bufferへ直接出力 | 条件付き・低優先 | PEPC推論は1.813→1.639秒（9.6%短縮）。PGK・PEPC×4は改善なし。全出力・境界条件は最大差0だが、一般的な効果は未確認 |

案1、2、10は同じendpoint処理に関係する。案4と8も異なる保存経路である。
上表の短縮率を足したり掛けたりして、組合せ時の効果を推定することはできない。

## 調査・計測方法

基準は `4498c436b58c205dc4e10e6d96549b8bb6e805bf`（1.16.20）。
macOS 27.0.1 arm64、Python 3.14.7、NumPy 2.5.3、SciPy 1.17.1、pandas 3.0.5。
[文献調査と選定根拠](literature.md)では、系統尤度計算、行列指数、配列・データフレーム処理、
ディスク入出力、重み付き非復元抽出の一次論文・公式資料を確認した。
過去の調査だけで判断せず、現行実装・呼出し元を確認した。
案7の当初のID解析削減は既実装と判明したため、残る不要集計の削減へ改訂した。

**別々の10個のサブエージェントが1案ずつ担当**した。
同時稼働枠に合わせて順次割り当て、CPU負荷を伴う計測は
[共通lock](bench_common.py)で直列化した。親エージェントが採否・数値・根拠を照合し、
案9にはbytesの直接比較を追加させた。
NumPy/SciPy import前にBLAS/OpenMPのスレッド数を1へ指定した。
1回のwarmup後、実行順序を交互にして3回計測し、wallとCPUを記録した。

PGKは33配列×417コドン、PEPCは71配列×971コドン。
同梱の固定IQ-TREE fitを使い、新しいfit・ネットワーク・描画は除外した。
解析出力は新しい一時ディレクトリへ保存した。
PEPC×4はサイトを反復した合成サイズ条件であり、独立した生物学的標本ではない。
案9も実ASRVではなくサイト数相当の合成重みである。
小さな差や測定範囲の重複は、確実なwall改善と扱わなかった。

各案の `.py` が再現可能な試作、`.json` が環境・入力・全計測値・比較結果、
`.md` が一次資料・採否・制約・再現コマンドを記録する。
処理ごとに消費・保存する配列が異なるため、別案のbaseline時間同士は比較しない。
メモリについても、明示配列bytes・累積割当て量・process peak RSS・全体物理RAMを区別した。

## 検証と残る範囲

全案で現行との直接比較を行った。案3は精度不一致を検出して見送った。
他案では、それぞれの比較対象の出力・エラー・所有権等の検査に成功した。
追加で試作をメモリ内へ適用した既存テストは、案8がstorage **10 passed**、
案9がFisher関連 **2 passed・17 deselected**、案10がendpoint **26 passed**。
案9の独立参照はFractionによる全組合せ列挙、案3は高精度Decimal参照も使った。

最終チェックのコマンド・結果は [checks.json](checks.json) に保存する。
製品コードを変更していないため通常の全pytest・test-fast・typecheckは実行していない。
installed wheel、source-only配布物、sanitizer、Linux性能基準、実IQ-TREE再推定、
GPU/構造モデル、全科学的校正を検証したという結果でもない。
採用案を製品へ組み込む際は、対応する単体・統合・科学的parity・native/fallbackと、
実CLI全体の性能を改めて確認する必要がある。
