# joint推定のRAM削減（2026-09-11）

`212371b`を基準に、同じjointモデル・入力・出力設定でRAM削減を測定した。
全統計のarity=2検索、指定枝のsites、大きなscan配列の保持方法を変更し、
事後確率や要求された統計量を省略せずにピークRAMを減らした。

## 測定結果

値は3回の中央値。括弧内は最小–最大。RAMはMiB、時間は秒。

主要3ケースでRAMが約47–86%減った。scanは一時ファイルI/Oを伴い、
時間の中央値は約7%増えた。通常検索の時間・RAMは測定のばらつきの範囲で、
大幅な増加はなかった。これらは固定fitの限られた入力による結果であり、
他の枝数・サイト数・出力設定で同じ削減率を保証するものではない。

実行は共有ホスト上で行い、各回のホストCPU利用量をJSONに記録した。
とくに全統計検索の変更前時間は44.6–63.3秒とばらつくため、速度倍率の
細かな値よりも、一貫したRAM削減と時間範囲を重視する。

## 測定方法

- macOS 26.6.2、x86_64、64 GiB RAM、Python 3.10.14、NumPy 1.26.4、
  SciPy 1.15.2、pandas 2.2.3。同じPython環境とnative拡張を両版で使用。
- 各ケースはウォームアップ1回、その後3回。変更前後の順序を交互にして、
  独立したCLIプロセスを逐次実行。スレッド数・BLASスレッド数はともに1、seed=8。
- `/usr/bin/time -l`のmaximum resident set sizeとCLI全体の経過時間を測定。
  時間には起動・入力・出力を含む。OSのファイルキャッシュは消去していない。
- PGKは33配列×417コドン、PEPCは71配列×971コドン。
  PEPC×4は配列とサイト別情報を4回繰り返した3,884コドンの合成サイズ試験。
  モデル・枝長は元のIQ-TREE 2.3.6による固定fit（ECMK07+F+R4）を再利用する。
  IQ-TREEの再推定、ネットワーク取得、プロットは対象外。
- scanの性能測定は校正なし。既定の1,000反復校正全体の性能を示すものではない。
  sitesは枝0,2、状態カテゴリ図なし。各CLIの完全な引数、入力・ソースのSHA-256、
  各回の値とホストCPU利用状況は[results.json](results.json)に記録した。

## 実装と適用範囲

1. arity=2の全統計検索では、`spe2spe`もサイトブロックごとに枝ペアへ集計し、
   全サイトの詳細イベントを保持しない。64 MiBの集計用workspace見積もりに
   合わせてブロックを縮める。入力・推定処理全体のRAMを64 MiBに制限するものではない。
2. sitesでは指定枝の詳細イベントと全枝の小さなサイト集計を保持する。
   状態カテゴリ図、VEP、正の`min_sub_pp`、集合式の`A`を必要とする設定は
   引き続き必要な全枝の詳細を保持する。
3. joint scanではイベントとカテゴリ別状態の合計が64 MiBを超える場合、
   損失のないサイト順の一時ファイルを使用する。書き込みブロックは原則32 MiB以下、
   読み込みは小さなブロックまたは1サイト。単一サイト自体が大きい場合はその大きさが下限になる。
   PEPCでは約0.657 GiBの一時ファイルが必要。`CSUBST_TMPDIR`で配置先を指定できる。
   ファイルは所有する配列／実行の終了に伴って削除され、校正workerは親の完成済みファイルを読む。

全ノードの周辺状態などは引き続きRAMに残り、入力規模に応じて増える。
高arityでの全統計、追加の詳細集計が必要な検索、CTMC bridgeの保持方式は対象外。
詳細は[endpointの説明](../../docs/ENDPOINT_POSTERIORS.md)を参照。

## 正しさの確認

各ケースのウォームアップ出力を変更前後で照合し、主結果TSVの全列・行順・型を
比較した。数値の許容差は`rtol=1e-8, atol=1e-9`。統計量の削減や丸め精度の変更はない。
実行時間などの動的メタデータは比較対象から除外した。
全統計検索の8,446枝ペア（50列）、scanの103行（121列）とunit表、
sitesの971サイト（41列）を含む。全統計検索の主要数値列の最大絶対差は
`2.71e-9`で、集計順序による浮動小数点差の範囲だった。

- 通常テスト2,236件成功、5件skip。nativeテスト16件成功。
- Ruff、repository hygiene、documentation check成功。
- 型検査は任意配列の存在を明示するassertを追加後、全23対象で成功。
  その修正後にscan CTMCテスト24件を再確認。
- native拡張を無効にした関連テスト140件成功、native専用9件skip。
- ファイル保存と配列保存の同等性、閾値適用、rate mixture、複数processの校正、
  ファイル所有期間と解放、ゼロサイトもテストした。

## 再現

[benchmark.py](benchmark.py)は既存の固定fit CLIハーネスを使用し、全列比較を追加する。
変更前を`212371b`、変更後をこのレポートを含むコミットから別ディレクトリへ展開し、
同じ環境でnative拡張を用意して実行する。必要な同梱データはハーネスが基準側から取得する。

```sh
python reports/memory_optimization_20260911/benchmark.py \
  --baseline-root /path/to/before --candidate-root /path/to/after \
  --baseline-label 212371b --candidate-label memory-optimized \
  --cases pepc_full pepc_scan_defaults pepc_sites pgk_defaults pepc_defaults pepc4_defaults \
  --workdir /tmp/csubst-memory-benchmark \
  --result /tmp/csubst-memory-results.json
```
