# 案09: 独立枝組合せ数の中間状態を早期解放

**採用推奨（メモリ削減）**。`count_independent_branch_combinations` の2箇所の
子状態取得を辞書の `pop` に変える。親に取り込まれた子状態を保持し続けず、
同じ整数演算を同じ順序で実行する。木では各子に親が1つだけあるため、
取り込んだ子状態の再利用は不要。公開API、返り値のPython整数、エラーは維持する。

実装は [proposal09.patch](proposal09.patch)、再実行可能な検証は
[proposal09.py](proposal09.py)、反復ごとの生データは
[proposal09.json](proposal09.json)。この独立検証では本体・testsを変更していない。

```sh
python reports/performance_round3_20261023/proposal09.py
```

基準は commit `624bb8a6dae536d0fa10891f666684ef1ad3dab0` の明示snapshot。
`CSUBST_PERF_BASELINE` にsnapshot rootを指定でき、未指定時は共有pointerを読む。
sourceのSHA-256をJSONに記録し、作業中の本体から関数を取得しない。
環境はPython 3.14.7、macOS 27.0.1 arm64、12 logical CPUs、NumPy 2.5.3、
SciPy 1.17.1、pandas 3.0.5。import前にBLAS/OpenMP thread数を1に固定し、
入力生成・正しさ確認・計測全体を `bench_common.benchmark_lock()` で直列化した。

正しさは **568ケース一致**。うち400ケースは、祖先・子孫と姉妹関係から
禁止ペアを独立に構成し、枝集合を全列挙した期待値と両実装を比較した。
root-only、unary、balanced、pectinate、star、polytomous、乱数で生成した小木、
両 `exclude_sister_pair` モード、arity 0・負値・枝数超過を含む。
負値の例外型と文言、全返り値がPython `int` であることも検査した。
大きい木では最大 **322 bit** のカウントまで一致し、starは二項係数とも照合した。

各条件で両実装を1回warmupした後、実行順を反転しながら7反復を測定した。
短い呼び出しは40 ms CPUを目標に1–40回まとめ、時間を1呼び出しへ正規化した。
メモリは別に順序交互の3回 `tracemalloc` peakを取り、その中央値を示す。
入力木やimport済みmoduleは測定外で、native allocatorやRSSは含まない。

balancedやpectinateでは明確にメモリを減らし、starでは効果が小さい。
小さい実データ木は絶対節約量が数十KBで、CPUは3–7%増（約4–50 μs）。
大木のCPU比は0.84–1.03で、wallとCPUの乖離もあるため、
全トポロジー共通の高速化は主張しない。
2行の取得方法変更で最大約8.4 MBの一時Python割当を抑えられるため、
メモリ改善としては保守コストに見合うと判断する。

独立検証時点ではpytest・full CLI・installed-wheel・科学的校正は未実施。
この変更は組合せの整数カウントだけを扱い、推定量・閾値・参照データは変更しない。
採用時は既存の組合せカウントunitテストと `main_inspect` の出力テスト、
リポジトリのチェックentrypointを主担当が追加確認する。
